# Scan benchmark

Measured with `cgs benchmark <folder> --changed 50` (corrective audit §7: measure before optimizing). Each benchmark
runs a cold full analysis, a rescan without change, and a rescan with 50 files re-extracted (simulated: their cached
facts are ignored; the sources are never modified). Raw reports: the JSON files next to this page.

**Machine:** Windows-11-10.0.26200-SP0, 8 logical CPUs, Python 3.12.10; CodeGraph-Sci 0.1.0;
7 worker processes (default: CPU count - 1); no other activity during the runs (October 17, 2026). Earlier runs made
while the test suite was running were discarded: they were up to 2x slower.

## Findings

- The incremental target of the architecture (rescan after 50 changed files in less than 30 s) is reproduced on this
  machine: 10.8–10.9 s on the synthetic code base, 25.9 s on the Code_Aster sample. It is a measurement on one
  machine, not a guarantee for slower ones: `test_synthetic_full_size` failed several times at 30.6–34.9 s while the
  machine was busy.
- A rescan is dominated by the complete rebuild that follows extraction, not by extraction: on Code_Aster, cache
  lookup 5.9 s, inventory 4.9 s, index 7.8 s and SQLite write 3.9 s, against 1.8 s of extraction for 50 files. Any
  incremental optimization should target these phases first (and measure them again).
- `extract_full_ms` and `extract_outline_ms` add up the time of every file over all workers (CPU time), while
  `extract_wall_ms` is the elapsed time: on a cold Code_Aster analysis, 440 s of extraction work run in 69 s.
- On a very small project, worker start-up dominates (about 0.6 s per analysis): the price of the per-file deadline.
